# Plan: Secrets — keeping private material out of a public repo

Revision 1. **Decision deferred by design.** Referenced by [`foundation.md`](foundation.md); to be settled after the Omarchy foundation and zsh sections are working, not before.

## Problem

`fernandoaleman/nix-config` is public, so nothing private can ever be committed — not encrypted, not obfuscated. The reference repo (`fernandoaleman/dotfiles`, private) currently carries 23 encrypted files plus work configuration that must all find another home:

| Material | Files | Notes |
|---|---|---|
| SSH keypairs | 17 | Five per-environment work keypairs, one sandbox keypair, one personal key, `authorized_keys` |
| AWS config | 3 | `config`, `config.sso`, credentials template |
| VPN profile | 2 | OpenVPN client profile |
| API tokens | 1 | Shell exports consumed by CLIs |
| jira CLI config | 1 | ~250 lines generated by `jira init` against one Atlassian instance |
| confluence CLI config | 1 | Five fields — domain, API path, token, auth type, email |

The two CLI configs are *not* secrets, but they are employer-identifying and machine-generated, so they travel with the secrets rather than being rebuilt in Nix.

## Constraint from the rest of the design

The bootstrap ordering in `foundation.md` depends on this section **not** being required to reach a working machine:

```
clone public repo -> home-manager switch -> working shell, editor, terminal, git
                  -> THEN authenticate -> retrieve private material
```

So whatever is chosen must be an explicitly-invoked second step, never a dependency of the first `switch`. A solution that makes the initial build fail without credentials has broken the property the public repo exists to provide.

## Candidate approaches

Not yet evaluated. Listed so the decision starts from a known field rather than from scratch:

- **1Password CLI at runtime.** `op read` calls resolve secrets when a shell starts or a script runs; nothing is ever at rest on disk. Already in use for some material. Costs a `op signin` dependency in the shell startup path, which needs care so a non-authenticated shell degrades rather than hangs.
- **Thumb drive, as previously used.** Private material lives on removable media and is copied in deliberately. Was the earlier habit, predating chezmoi. Simple, offline, no vendor — but manual, and the existing `backup-to-thumb-drive` / `import-from-thumb-drive` scripts survive the audit and already implement most of it.
- **sops-nix or agenix.** The idiomatic Nix answers. Both let *encrypted* files be committed with the key supplied out-of-band. Rejected for employer material on the grounds in `foundation.md` — ciphertext hides values but not structure, and file names alone would publish host and role naming. Could still suit purely personal secrets.
- **A private flake input.** A second, private repository consumed as an input. Deliberately rejected in `foundation.md` as permanent overhead, but it remains the fallback if the runtime approaches prove unworkable.
- **Out-of-band directory, unmanaged.** `~/.config` paths that Nix simply never declares, populated by hand or by one of the above. The least clever option and possibly the right one for the two CLI configs.

## Open questions

1. Which approach — to be decided after Omarchy is up, with the tradeoffs assessed against how the machine actually feels to use.
2. Do personal and employer secrets want the *same* mechanism, or is it reasonable to split them — for instance sops-nix for personal material committed to the public repo, and something out-of-band for work?
3. SSH keys specifically: generated per machine and registered, or carried between machines? Carrying them is what the current setup does; generating them per machine is better practice and removes the largest category entirely.
4. What does a *new* machine's very first authenticated action look like, and is it documented well enough to follow under pressure with no working environment?
