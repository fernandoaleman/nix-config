# Plan: Secrets — 1Password, the way Omarchy already expects

Revision 3. Referenced by [`foundation.md`](foundation.md). Revision 1 deferred the decision; revision 2 chose 1Password but rejected its SSH agent on a claim that turned out to be false.

## Problem

`fernandoaleman/nix-config` is public, so nothing private is ever committed — not encrypted, not obfuscated. The reference repo (`fernandoaleman/dotfiles`, private) carries material that must find another home:

| Material | Count | Notes |
|---|---|---|
| SSH keypairs | 17 | Personal, sandbox, and several shared with a team through a cloud provider |
| AWS config | 3 | `config`, `config.sso`, credentials template — account identifiers and role names |
| API tokens | 1 | Shell exports consumed by CLIs |
| jira CLI config | 1 | ~250 lines, machine-generated by `jira init` |
| confluence CLI config | 1 | Five fields, one a token |
| ~~VPN profile~~ | ~~2~~ | **Out of scope.** The `.ovpn` is in 1Password and the client profile is made by hand, once per machine |

Much of this is not secret in the cryptographic sense. AWS account identifiers, role names and the two CLI configs are *employer-identifying* rather than confidential; they travel with the secrets because they cannot be committed either.

## Constraint from the rest of the design

The bootstrap ordering in `foundation.md` depends on this section **not** being required to reach a working machine:

```
clone public repo -> home-manager switch -> working shell, editor, terminal, git
                  -> THEN authenticate -> retrieve private material
```

Whatever is chosen must be an explicitly-invoked second step. A design that makes the first `switch` fail without credentials has destroyed the property the public repo exists to provide.

## Omarchy already has an opinion here

This is the deciding factor, and revision 2 missed it through a careless search. 1Password is **first-class in Omarchy Quattro**, in three places:

```
omarchy-menu.jsonc:213   install.service.1password -> omarchy-install-service-1password
applications.lua:20      SUPER + SHIFT + /  "Passwords" -> 1password
fns/rsyncing:5           "Reuse one SSH connection per login,
                          so 1Password only prompts once."
```

The installer pulls `1password` *and* `1password-cli`, wires up the Chromium extension, and launches the app under `uwsm`. The keybinding is dedicated. And that comment in `fns/rsyncing` is the telling one: Omarchy's rsync watchers set up SSH connection multiplexing (`ControlMaster=auto`, `ControlPersist=yes`) **specifically because the 1Password SSH agent prompts**.

Omarchy is not merely tolerant of 1Password — its shell helpers are written around the agent's behaviour. By comparison Bitwarden gets a menu entry and window rules and nothing else.

Revision 2 claimed *"Omarchy Quattro installs no password manager"* and rejected the agent partly on an unverified Wayland story. The first half was wrong; the second is answered by Omarchy shipping the installer.

## Chosen design

**1Password, with its SSH agent, installed the way Omarchy installs it.**

### SSH keys: the agent, not files

*"Your private key never even leaves the 1Password app."* Keys stay exactly as they are — same public keys, already deployed across dozens of servers, nothing to re-register. That matters because several keypairs are **shared by a team** rather than owned, so regenerating them was never available.

`programs.ssh.matchBlocks."*".identityAgent` carries it, and the path can be identical on both machines:

```
Linux   ~/.1password/agent.sock
macOS   ~/Library/Group Containers/2BUA8C4S2C.com.1password/t/agent.sock
        -> 1Password documents symlinking this to ~/.1password/agent.sock
```

With that symlink the `~/.ssh/config` line is the same on both, so it lives in a shared module rather than a host.

**Approval is per session, not per connection.** Default is *per key, per application*: approve once and that grants the app "and all its subprocesses for the entire agent session". A terminal approved once covers every `ssh`, `git push` and `scp` from it. The cost, named plainly: when 1Password locks, keys leave memory, so the next SSH prompts for an unlock. Against today's unencrypted keys-on-disk that is one extra interaction per lock; against properly passphrase-protected keys it is a wash.

**Team-shared vaults need `~/.config/1Password/ssh/agent.toml`.** By default the agent reads only Personal, Private and Employee vaults. That file is configuration rather than secret, so home-manager can own it and it works identically on both machines.

### Everything else: a committed manifest

A TOML file in the repo lists `op://` references and destinations, modelled on the `.chezmoidata/onepassword.toml` pattern. Two sections now that SSH keys are the agent's job:

```toml
[documents]   # whole files: AWS config, jira and confluence configs
[secrets]     # single values: API tokens, read at runtime
```

**References use UUIDs for both vault and item.** Not a style choice: work material lives in a vault named after the employer, inside the personal account, and `op://` accepts UUIDs in place of names — so the manifest can be public while naming nothing.

```
op://<vault-uuid>/<item-uuid>/<field>
```

The **left-hand keys are the only disclosure**, and they are chosen here rather than by 1Password, so they stay neutral. A reader learns what *kinds* of secret exist and nothing more, which is acceptable for a public repo and worth knowing is the case.

`builtins.fromTOML` reads the manifest at evaluation time and a `writeShellScriptBin` derivation is generated from it, so adding an entry is one line of TOML with no hand-maintained shell to drift. It is invoked explicitly — never from `home.activation`, which would run on every switch and reintroduce the credential dependency.

### Nothing secret passes through home-manager

A hard constraint, not a preference. Everything home-manager writes goes through the Nix store first, and the store is world-readable:

```
/nix/store        drwxrwxr-t  root:nixbld
a managed file    -r--r--r--  root:root
```

Any user on the machine can read anything `home.file` produces. A private key placed there is published locally. This is also why the agent suits the design: with it, no private key is ever written anywhere.

### Installation, per platform

The GUI is required for the agent, and is installed **the platform's way** on each machine rather than through the flake:

- **Omarchy** — `omarchy-install-service-1password`, or the menu entry. It installs both packages, wires the Chromium extension, and launches under `uwsm`. Nix cannot script this and should not: it is `sudo pacman` plus writes under `/usr/share`, and putting that in `home.activation` would make every `switch` demand root. It belongs in [`bootstrap.md`](bootstrap.md) alongside the `@nix` subvolume as a one-time manual step.
- **macOS** — the App Store or 1Password's own installer. nixpkgs lists `_1password-gui` for `aarch64-darwin` and it is not marked broken, but macOS 1Password needs proper app registration for the SSH agent, Touch ID unlock and browser integration; a Nix-installed bundle is a poor fit.

The **CLI** comes from the flake on both (`_1password-cli` 2.39.0, darwin and Linux), so it is pinned and identical. The SSH config, `agent.toml` and manifest are all shared modules.

Omarchy separately ships `gnome-keyring` and `libsecret`, which own `org.freedesktop.secrets`. That is the freedesktop Secret Service for applications that need to stash a credential, not a password manager, and 1Password neither replaces nor conflicts with it.

## Rejected approaches

- **Keys on disk, written by `op read`.** The fallback if the agent proves annoying, and genuinely reasonable: `?ssh-format=openssh` yields a key file, needs only the CLI with no GUI, and carries exactly the risk the status quo already does. Rejected because Omarchy's integration makes the agent the better-supported path, and because a private key that never touches disk is strictly safer. **Fully reversible** — same vault, same items, only the consumer changes.
- **sops-nix or agenix.** The idiomatic Nix answers, and wrong here. Ciphertext hides values but not structure: committed filenames and manifest keys would publish environment and role naming even with every value encrypted.
- **A private git repo, age-encrypted, cloned by Nix.** Needs **two roots of trust** — an SSH key to clone and an age key to decrypt — where every scheme needs at least one and a second is pure cost. Circular for the largest category: an SSH key would be needed to fetch the SSH keys. And as a flake input it breaks evaluation without credentials, violating the bootstrap constraint.
- **Thumb drive.** Revision 1 claimed the existing `backup-to-thumb-drive` / `import-from-thumb-drive` scripts "already implement most of it". They do not: they rsync `~/Downloads`, `~/code`, `~/.claude` and shell history, contain no secret material, and hardcode `/Volumes/Backup`, which is macOS-only. (The filesystem objection to sharing a drive is also unfounded — exFAT is native on both — but the scripts are simply not about this.)
- **Generating SSH keys per machine.** Proposed and rejected on facts: the public keys are already deployed across dozens of servers, and several keypairs are shared by a team rather than owned, so they cannot be regenerated unilaterally.

## Open questions

1. **The `op` invocations are unverified.** `?ssh-format=openssh`, whether whole files want `op read` or `op document get`, and the exact `agent.toml` syntax for naming vaults by UUID. All read correct in the documentation; none has been run against a real vault.
2. **Which vault.** Work material already lives in a vault named for the employer inside the personal account; other material is spread elsewhere. Since references are UUIDs the manifest does not care, so a new vault is worth creating only if it helps *you* find things.
3. **What a new machine's first authenticated action looks like**, and whether it is documented well enough to follow under pressure with no working environment.
4. ~~Whether `user.email` moves into the manifest.~~ **Decided: it stays in `modules/git.nix`.** Moving it would leave a fresh machine with no git identity until `make secrets` ran, turning foundation.md's "clone → switch → working git" into "working git, minus identity" — a real cost against a future-proofing argument that a one-line commit already covers.
