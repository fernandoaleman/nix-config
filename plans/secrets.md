# Plan: Secrets — 1Password as the single source, fetched on demand

Revision 2. Referenced by [`foundation.md`](foundation.md). Revision 1 deferred the decision by design; this settles it.

## Problem

`fernandoaleman/nix-config` is public, so nothing private is ever committed — not encrypted, not obfuscated. The reference repo (`fernandoaleman/dotfiles`, private) carries material that must find another home:

| Material | Count | Notes |
|---|---|---|
| SSH keypairs | 17 | Personal, sandbox, and several shared with a team through a cloud provider |
| AWS config | 3 | `config`, `config.sso`, credentials template — account identifiers and role names |
| API tokens | 1 | Shell exports consumed by CLIs |
| jira CLI config | 1 | ~250 lines, machine-generated by `jira init` |
| confluence CLI config | 1 | Five fields, one of them a token |
| ~~VPN profile~~ | ~~2~~ | **Out of scope.** The `.ovpn` lives in 1Password and the client profile is created by hand, once per machine. Not worth automating |

Most of it is not secret in the cryptographic sense — AWS account identifiers, role names and the two CLI configs are *employer-identifying* rather than confidential. They travel with the secrets because they cannot be committed either.

## Constraint from the rest of the design

The bootstrap ordering in `foundation.md` depends on this section **not** being required to reach a working machine:

```
clone public repo -> home-manager switch -> working shell, editor, terminal, git
                  -> THEN authenticate -> retrieve private material
```

Whatever is chosen must be an explicitly-invoked second step. A design that makes the first `switch` fail without credentials has destroyed the property the public repo exists to provide.

## Rejected approaches

- **sops-nix or agenix.** The idiomatic Nix answers, and wrong here. Ciphertext hides values but not structure: committed filenames and manifest keys would publish environment and role naming even with every value encrypted. Viable for purely personal material, which turns out not to need it.
- **A private git repo, age-encrypted, cloned by Nix.** Considered seriously. It needs **two roots of trust** — an SSH key to clone the repo *and* an age key to decrypt — where every scheme needs at least one and adding a second is pure cost. It is also circular for the largest category: you would need an SSH key to fetch your SSH keys. And as a flake input it breaks evaluation without credentials, violating the bootstrap constraint above.
- **Thumb drive.** Revision 1 claimed the existing `backup-to-thumb-drive` / `import-from-thumb-drive` scripts "already implement most of it". They do not: they rsync `~/Downloads`, `~/code`, `~/.claude` and shell history, contain no secret material at all, and hardcode `/Volumes/Backup`, which is macOS-only. (The filesystem objection to sharing a drive between the two machines is unfounded — exFAT is native read/write on both — but the scripts are simply not about this.)
- **Generating SSH keys per machine.** Proposed, and rejected on facts: the public keys are already deployed across dozens of servers, and several keypairs are **shared by a team** rather than owned, so they cannot be regenerated unilaterally. This removed the largest simplification available and is why the design carries keys rather than minting them.
- **The 1Password SSH agent.** Genuinely better on security — *"your private key never even leaves the 1Password app"* — and rejected on cost. It requires the 1Password **desktop app**, which would mean a GUI dependency on Omarchy for a CLI workflow, with an unverified story under Hyprland and Wayland. It also prompts once per session and again after each lock, where the current workflow has no prompts at all. Keys on disk are exactly as safe as the status quo and need only the `op` CLI. The two are interchangeable later: same vault, same items, different consumer.

## Chosen design

**1Password is the single source. A committed manifest names what to fetch; an explicit command fetches it.**

### Nothing secret passes through home-manager

This is a hard constraint, not a preference. Everything home-manager writes goes through the Nix store first, and the store is world-readable:

```
/nix/store        drwxrwxr-t  root:nixbld
a managed file    -r--r--r--  root:root
```

Any user on the machine can read anything `home.file` produces. A private key placed there is published locally. So secrets are written by a script directly to their destination, never declared as home-manager files — which is also precisely what the bootstrap constraint requires.

### The manifest

A TOML file in the repo, modelled on the `.chezmoidata/onepassword.toml` pattern, listing `op://` references and destinations. Three sections, because the material behaves in three ways:

```toml
[ssh_keys]    # -> ~/.ssh/<name>, 0600, via ?ssh-format=openssh
[documents]   # -> whole files: AWS config, jira and confluence configs
[secrets]     # -> single values, read at runtime rather than written to disk
```

**References use UUIDs for both vault and item.** Not a style choice: work material lives in a vault named after the employer, and `op://` accepts UUIDs in place of names, so the manifest can be public while naming nothing.

```
op://<vault-uuid>/<item-uuid>/<field>
```

The **left-hand keys are the only thing the manifest discloses**, and they are chosen here rather than by 1Password — so they stay neutral. `work_bastion`, not anything naming an employer, environment or role. A reader learns what *kinds* of secret exist and nothing more, which is acceptable for a public repo and worth knowing is the case.

### Nix reads the manifest; the script is generated

`builtins.fromTOML` reads it at evaluation time, and a `writeShellScriptBin` derivation is generated from it. Adding a key is one line of TOML, with no hand-maintained shell to drift from the list. The result is invoked explicitly — never from `home.activation`, which would run on every switch and reintroduce the credential dependency the bootstrap constraint forbids.

### Only the CLI is needed

`op` authenticates headlessly, so nothing here requires the 1Password desktop app on either machine. `_1password-cli` 2.39.0 is in nixpkgs for `aarch64-darwin` as well as Linux, so both machines install the same pinned version from the same flake.

### What Omarchy provides, and does not

Omarchy Quattro installs **no password manager**. It ships `gnome-keyring` and `libsecret` — the freedesktop Secret Service, which owns `org.freedesktop.secrets` and exists for applications that need to stash a credential. It offers Bitwarden through a menu entry (`when: ! omarchy-pkg-present bitwarden`) and ships window rules for it, but installs nothing. There is no Omarchy-blessed secrets manager to diverge from, and 1Password is purely additive.

## Open questions

1. **Moving `user.email` into the manifest has a cost worth naming.** It is currently committed in `modules/git.nix` — a personal address already public in this repository's own history. Moving it means a fresh machine has *no git identity* until `make secrets` runs, so `git commit` fails until then, and `foundation.md`'s "clone → switch → working git" becomes "working git, minus identity". The mechanism would be `programs.git.includes` pointing at a file the script writes, which git silently ignores when absent. Worth confirming that trade is wanted, given changing an address in a one-line commit is not obviously harder than changing it in 1Password and re-running on two machines.
2. **The `op` invocations are unverified.** `?ssh-format=openssh`, whether `op item list --categories "SSH Key"` behaves as documented, and whether whole files want `op read` or `op document get`. All read correct in the documentation; none has been run against a real vault. To be settled before the script is generated rather than guessed at.
3. **Which vault.** Work material already lives in a vault named for the employer inside the personal account; other material is spread across other vaults. Since references are UUIDs, the manifest does not care — so a new vault is only worth creating if it helps *you* find things, not for any technical reason.
4. **What a new machine's first authenticated action looks like**, and whether it is documented well enough to follow under pressure with no working environment. Unchanged from revision 1.
